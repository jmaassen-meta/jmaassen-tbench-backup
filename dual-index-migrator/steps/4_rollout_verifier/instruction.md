Rollout API — dual_index/rollout.py (all file-backed at `<base_dir>/rollout.json`)

| Function | Signature | Behavior |
|---|---|---|
| rollout_status | `rollout_status(base_dir)` | Reads the rollout state file at `<base_dir>/rollout.json` and returns a dict `{"phase": "not_started"|"canary"|"partial"|"full", "shards_migrated": [...], "total_shards": N, "verified": bool}`. If no state file exists, returns `{"phase": "not_started", "shards_migrated": [], "total_shards": N, "verified": False}`. The file, when present, is JSON like `{"phase": "canary", "shards_migrated": [0], "total_shards": 8}`. |
| advance_rollout | `advance_rollout(base_dir, num_shards, target_phase)` | Advances the rollout to the target phase by atomically updating `<base_dir>/rollout.json`. **Exact shard lists (must match):** `canary` is exactly `[0]` (1 shard), `partial` is exactly `[0, 1, ..., N//2 -1]` (floor half, e.g., N=8 → `[0,1,2,3]`), `full` is exactly `[0, 1, ..., N-1]` (all shards). Phases are ordered `not_started < canary < partial < full` and advancing must be **monotonic and stepwise** — you may only move to the immediate next phase: `not_started → canary → partial → full`. Any other transition must fail with `ValueError` without touching `rollout.json` (e.g., `not_started → partial` must fail, `canary → canary` must fail, `partial → canary` must fail, `canary → full` must fail, `full → partial` must fail). On success returns the new status dict like `{"phase": "canary", "shards_migrated": [0], "total_shards": 8, "verified": True}`. **Lock handling (do this first):** Hidden tests pre-create a file-backed hold marker `<base_dir>/.hold_<username>` to simulate a row locked outside the CLI. If that file exists, any operation on that username must be treated as locked. For rollout, you must ensure no username that belongs to a target shard is locked. To determine which shard a username belongs to, use stable hashing `int(hashlib.md5(username.encode()).hexdigest(), 16) % num_shards` (this matches the per-username lock placement in prior steps). Check in order: (1) scan `base_dir` for files matching `.hold_*`; for each such file extract username after `.hold_` and if its hash is in `target_shards`, fail immediately with `ValueError` without modifying `rollout.json`; (2) then collect all usernames that actually exist in `base_dir/ig/shard_*.json` and `base_dir/threads/shard_*.json` whose hash is in `target_shards`, and if any of those has `<base_dir>/.lock_<username>` or `<base_dir>/.hold_<username>` present, fail with `ValueError` without modifying `rollout.json`. Only after lock checks are clean should you run the consistency checks: call `verify(base_dir, num_shards)` and require `verify["inconsistent"]==0`, then `backfill(base_dir, num_shards)` and require `needs_backfill==0` and `inconsistent==0`, then `gc_dangling(base_dir, num_shards)` and require `dangling_found==0`. If any of those is non-zero, raise `ValueError` without modifying `rollout.json`. Only when all checks pass should you atomically write `{"phase": target_phase, "shards_migrated": target_shards, "total_shards": num_shards, "verified": True}` to `<base_dir>/rollout.json` (overwrite if exists). |
| rollout_verify | `rollout_verify(base_dir, num_shards)` | End-to-end verification of the entire migration: runs `verify` across all shards and universes and blobs, checks that `backfill` shows `needs_backfill==0`, that `gc_dangling` shows `dangling_found==0`, and that `rollout_status` is at least `partial` with all `shards_migrated` verified. Returns a dict `{"overall": bool, "verify": {...}, "backfill": {...}, "gc": {...}, "rollout": {...}}`. `overall` is `True` only if `verify["inconsistent"]==0` and `backfill["needs_backfill"]==0` and `gc["dangling_found"]==0` and `rollout["phase"]` is at least `partial` with all `shards_migrated` verified. Does not modify data. |

Storage detail — keep it simple and deterministic: the rollout state is a JSON file at `<base_dir>/rollout.json` with keys `phase`, `shards_migrated`, `total_shards`, `verified`. Exact values: `canary` → `{"phase": "canary", "shards_migrated": [0], "total_shards": N, "verified": True}`, `partial` → `[0,1,...,N//2-1]` e.g., N=8 → `[0,1,2,3]`, `full` → `[0,...,N-1]`. Advancing is monotonic and stepwise `not_started → canary → partial → full` — you cannot skip or repeat or go backwards, so `not_started → partial` must fail, `canary → canary` must fail, `partial → canary` must fail, `canary → full` must fail. All operations are file-backed, deterministic, and offline. `advance_rollout` must fail without modifying `rollout.json` if any username in the target shards is locked, **and** must check locks before consistency, then verify the entire store is consistent (verify, backfill, gc all clean) before writing.

Hint — `advance_rollout` sketch (shows file contract, not prescriptive): first build `target_shards = [0] if phase=="canary" else list(range(N//2)) if phase=="partial" else list(range(N))`, then check locks first — scan `Path(base_dir).glob(".hold_*")`; for each hold file get username after `.hold_` and compute `int(hashlib.md5(username.encode()).hexdigest(), 16) % N`; if that hash is in `target_shards`, raise `ValueError` without touching `rollout.json`; then collect usernames from `base_dir/ig/shard_*.json` and `threads` whose hash is in `target_shards` and if any has `.lock_<username>` or `.hold_<username>`, raise `ValueError`; only then run `v = verify(base_dir, N); if v["inconsistent"]!=0: raise`, `b = backfill(base_dir, N); if b["needs_backfill"]!=0 or b["inconsistent"]!=0: raise`, `g = gc_dangling(base_dir, N); if g["dangling_found"]!=0: raise`; only then atomically write the phase JSON to `<base_dir>/rollout.json`. This order ensures a hold marker blocks canary even if verify would also fail, which is what hidden tests check.
