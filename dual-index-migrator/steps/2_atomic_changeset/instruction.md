Now that the single and dual record formats and sharded storage are in place, let's add atomic cross-universe and cross-shard operations — the pattern that made the 1.5B/day username service hard. In production the username index is split by universe: IG and Threads each have their own sharded store, so even a single logical username touches two physical shard trees.

Please extend the model under /app/dual_index. The foundation from the previous step stays as-is (dual_index/encoding.py, dual_index/shard.py, dual_index/store.py, and the init/write/read commands). Hidden tests will import the exact new paths below via PYTHONPATH=/app.

| Module | Key symbols | Purpose |
|---|---|---|
| dual_index/atomic.py | AtomicIndex | Cross-universe, cross-shard atomic operations with per-row global locking |
| dual_index/cli.py (extended) | link, unlink, rename commands | Command-line entry points for atomic operations |

The store is now per-universe: under base_dir there are two sharded trees, one for IG and one for Threads (for example base_dir/ig and base_dir/threads, each containing its own sharded JSON files). A single-format username has an entry only in the IG tree; a dual linked username has entries in both trees under the same username key. The exact sub-directory names and internal file shapes are up to you, as long as the two universes are separate sharded stores under base_dir.

Atomic API — dual_index/atomic.py

| Class / Method | Signature | Behavior |
|---|---|---|
| AtomicIndex | AtomicIndex(base_dir, num_shards) | Wraps two sharded stores (IG and Threads) under base_dir with crash-safe atomicity and per-username serialization. Any username being operated on must be serialized across both universes until the operation is complete — either successfully committed or fully recovered from failure — so the next operation on that row sees a clean committed state. No explicit recover command is needed; recovery is automatic on next access. |
| link | link(username, ig_uid, threads_uid) | Atomically links a username: creates or updates the dual state by writing the username to both IG and Threads shards in one all-or-nothing operation. If the user is currently single-format (only in IG), it adds the Threads entry and updates the IG entry to linked; if already dual, it updates both entries to the new linked values. Must serialize on that username across both universes for the entire operation. If a crash occurs mid-operation, the crash handler must automatically clean up partial writes in either universe and return an error to the caller (raise an exception), leaving both stores in their pre-operation state. Because serialization is held until recovery completes, the next operation on that username sees a completed or fully recovered state without needing to trigger recovery itself. |
| unlink | unlink(username) | Atomically unlinks a username: removes the Threads entry and updates the IG entry to unlinked (threads_uid becomes None). For a single-format username, it first materializes the dual unlinked shape before removing. Must also serialize across both universes for the full operation with the same automatic crash recovery and error return. Raises ValueError if the username does not exist or is already unlinked. |
| rename | rename(from_user, to_user) | Atomically moves a username from one key to another, only if the destination is free in **both** IG and Threads shards, across both universes and across shards, and fails if `from_user == to_user`. It should check that `to_user` is absent in both universes and that `from_user` exists in at least one universe (IG entry must exist), then delete the `from_user` entries from both stores and create the `to_user` entries with the same record data but with `username` updated to `to_user`, preserving `ig_uid`, `threads_uid`, `link_state`, and `format`. The two usernames will almost always hash to different shards, so this is cross-shard, and because it touches both IG and Threads trees it is also cross-universe. Must serialize on *both* usernames for the entire operation, acquired in a fixed global order to avoid deadlock (e.g., `rename alice→bob` concurrent with `rename bob→alice` must not deadlock because both acquire locks in the same deterministic order), and release both only after commit or after crash recovery. If a crash occurs, the handler must automatically recover both universes and both locks and return an error, leaving both stores in their pre-operation state. Raises `ValueError` if `from_user` is absent, `to_user` is already taken in either universe, or `from_user == to_user`. |
| read | read(username) | Returns the decoded dual or single record or None, reflecting only committed state across both universes. It must respect ongoing serialization — if the row is currently locked by an in-flight atomic operation, it must not return a partial write. If a crash left a partial write for this username, `read` must silently auto-recover before returning: restore the pre-operation state and then return the committed value (`None` if absent) without raising — so the next mutating operation (`link`/`rename`) sees a clean state and can succeed without needing to handle pending itself. |

Storage and concurrency — keep it simple and deterministic. All operations must be crash-safe (partial writes are rolled back on next access), must serialize per username via a mechanism observable across separate CLI processes, must never leave a stale lock after success, failure, or crash recovery, and `rename` must lock both usernames in a deterministic global order to avoid deadlock. A pre-existing hold condition for a username (simulated by tests via an external marker) must cause operations on that username to fail with `ValueError` rather than hang. You choose the on-disk log/lock representation consistent with these guarantees — hidden tests verify only the observable behavior (atomicity, recovery, cross-process serialization, no stale locks, deadlock-free ordering), not the file names or log schema.

CLI — new commands on python -m dual_index.cli

| Command | Options | Behavior |
|---|---|---|
| link | --user NAME --ig-uid A --threads-uid B --base-dir PATH (default ./data) | Atomically links the user across both universes via AtomicIndex link. Serializes on that user across both stores for the duration, and on crash automatically recovers both universes and returns non-zero exit. |
| unlink | --user NAME --base-dir PATH | Atomically unlinks the user across both universes, same serialization and recovery, exiting non-zero on failure or recovered crash. |
| rename | --from USER --to USER --base-dir PATH | Atomically renames from_user to to_user across both universes and across shards, only if to_user is free. Serializes on both usernames in deterministic order for the entire operation, and on crash automatically recovers both universes and both locks and exits non-zero. |

Existing init, write, and read commands keep working as before, but init should now create the per-universe sharded trees and record shards and format. The new operations should be usable like python -m dual_index.cli link --user alice --ig-uid 100 --threads-uid 200 --base-dir ./data then python -m dual_index.cli read --user alice --base-dir ./data --output json showing a linked dual record, and python -m dual_index.cli rename --from bob --to alice --base-dir ./data only succeeding when alice is free in both universes, otherwise returning an error and leaving both stores unchanged.

Keep everything deterministic and offline. Hidden tests for this step will exercise link, unlink, and rename through both the Python API and the command-line tool, including simulated crashes and concurrent attempts on the same usernames (including rename with opposite order) to verify atomicity, crash recovery, and serialization without via direct file edits.
