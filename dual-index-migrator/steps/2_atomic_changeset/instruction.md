Now that the single and dual record formats and sharded storage are in place, let's add atomic cross-universe and cross-shard operations — the pattern that made the 1.5B/day username service hard. In production the username index is split by universe: IG and Threads each have their own sharded store, so even a single logical username touches two physical shard trees.

Please extend the model under /app/dual_index. The foundation from the previous step stays as-is (dual_index/encoding.py, dual_index/shard.py, dual_index/store.py, and the init/write/read commands). Hidden tests will import the exact new path below via PYTHONPATH=/app.

| Module | Key symbols | Purpose |
|---|---|---|
| dual_index/atomic.py | AtomicIndex | Cross-universe, cross-shard atomic operations with per-row global locking |
| dual_index/cli.py (extended) | link, unlink, rename commands | Command-line entry points for atomic operations |

The store is now per-universe: under base_dir there are two sharded trees, one for IG and one for Threads (for example base_dir/ig and base_dir/threads, each containing its own sharded JSON files). A single-format username has an entry only in the IG tree; a dual linked username has entries in both trees under the same username key (IG entry holds the IG uid, Threads entry holds the Threads uid, link_state is tracked with the IG entry). The exact sub-directory names and internal file shapes are up to you, as long as the two universes are separate sharded stores under base_dir.

Atomic API — dual_index/atomic.py

| Class / Method | Signature | Behavior |
|---|---|---|
| AtomicIndex | AtomicIndex(base_dir, num_shards) | Wraps two sharded stores (IG and Threads) under base_dir with a write-ahead log and per-username global locks. Any username being operated on must be globally locked across both universes until the operation is complete — either successfully committed or fully recovered from failure — so the next operation on that row is already clean. No explicit recover command is needed. |
| link | link(username, ig_uid, threads_uid) | Atomically links a username: creates or updates the dual state by writing the username to both IG and Threads shards in one all-or-nothing operation. If the user is currently single-format (only in IG), it adds the Threads entry and updates the IG entry to linked; if already dual, it updates both entries to the new linked values. Must hold the global lock for that username across both universes for the entire operation, write intent to the log for both writes, apply the shard writes, then commit and release. If a crash occurs mid-operation, the crash handler should automatically invoke recovery to clean up partial writes in either universe, release the lock, and return an error to the caller (raise an exception), leaving both stores in their pre-operation state. Because the lock is held until recovery completes, the next operation on that username sees a completed or fully recovered state without needing to trigger recovery itself. |
| unlink | unlink(username) | Atomically unlinks a username: removes the Threads entry and updates the IG entry to unlinked (threads_uid becomes None). For a single-format username, it first materializes the dual unlinked shape before removing. Must also hold the global lock across both universes for the full operation with the same automatic crash-handler recovery, lock release, and error return. Raises ValueError if the username does not exist or is already unlinked. |
| rename | rename(from_user, to_user) | Atomically moves a username from one key to another, only if the destination is free, across both universes and across shards. It should check that to_user is absent in both IG and Threads shards and that from_user exists, then delete the from_user entries from both stores and create the to_user entries with the same record data, all via the write-ahead log (WAL) with intents for each shard write. The two usernames will almost always hash to different shards, so this is cross-shard, and because it touches both IG and Threads trees it is also cross-universe. Must hold the global locks for *both* usernames for the entire operation, acquired in a fixed global order (for example sorted username) to avoid deadlock, and release both only after commit or after crash-handler recovery. If a crash occurs, the handler should automatically recover both universes and both locks and return an error, leaving both stores in their pre-operation state. Raises ValueError if from_user is absent or to_user is already taken. |
| read | read(username) | Returns the decoded dual or single record or None, reflecting only committed state across both universes. It should respect the global lock — if the row is currently locked by an in-flight atomic operation, it should not return a partial write. |

Storage and concurrency — keep it simple and deterministic: the log **must** be a file at `<base_dir>/wal.jsonl` (JSON lines) that records intent for each universe and shard write before the writes and a `commit` marker after — for example `{"id": "<uuid>", "op": "link", "username": "alice", "old_ig": null, "old_threads": null, "state": "intent"}` then `{"id": "<uuid>", "state": "commit"}`. Operations in this step may need to lock one username (link, unlink, read) or two usernames (rename), so to avoid deadlock any operation that locks two usernames must acquire those locks in a fixed global order such as `sorted([from_user, to_user])`. Whatever mechanism you use for the per-username lock, it **must** be file-backed at `<base_dir>/.lock_<username>` (for example `.lock_alice`) so that separate CLI processes observe it, and it must always be released after success, failure, or crash-handler recovery. Concurrent operations on the same username must not deadlock — a second operation that arrives while the row is locked should not block forever; it should eventually succeed on the recovered state or return an error, but not hang. For deterministic testing, hidden tests **will** pre-create a hold marker file at `<base_dir>/.hold_<username>` (for example `.hold_alice`) to simulate a held lock — if that file exists, operations on that username must treat the row as locked and return `ValueError` / non-zero exit.

Hint — minimal WAL/lock sketch (not prescriptive, but shows the file contract tests rely on): before any `ShardStore.put`/`delete`, append an `intent` line to `<base_dir>/wal.jsonl` like `{"id": "<uuid>", "op": "link", "username": "alice", "old_ig": ig_store.get("alice"), "old_threads": threads_store.get("alice"), "state": "intent"}` (for `rename`, include both `old_ig`/`old_threads` for `from_user` and `to_user`), then create `<base_dir>/.lock_<username>` (and for `rename`, both locks in `sorted([from_user, to_user])` order), apply the shard writes, then append `{"id": "<uuid>", "state": "commit"}` and remove the lock files; on entry to any operation, if an `intent` without `commit` exists, restore `old_ig`/`old_threads` snapshots, delete any partial writes, remove the lock files, and raise `ValueError` (so the next operation sees a clean state). The hold marker `<base_dir>/.hold_<username>` should be treated exactly like an existing `.lock_<username>` file.

CLI — new commands on python -m dual_index.cli

| Command | Options | Behavior |
|---|---|---|
| link | --user NAME --ig-uid A --threads-uid B --base-dir PATH (default ./data) | Atomically links the user across both universes via AtomicIndex link. Holds the global lock for that user across both stores for the duration, and on crash automatically recovers both universes, releases the lock, and exits non-zero. |
| unlink | --user NAME --base-dir PATH | Atomically unlinks the user across both universes, same locking and recovery, exiting non-zero on failure or recovered crash. |
| rename | --from USER --to USER --base-dir PATH | Atomically renames from_user to to_user across both universes and across shards, only if to_user is free. Holds both usernames' global locks in sorted order for the entire operation, and on crash automatically recovers both universes and both locks and exits non-zero. |

Existing init, write, and read commands keep working as before, but init should now create the per-universe sharded trees (for example base_dir/ig and base_dir/threads) and record shards and format. The new operations should be usable like python -m dual_index.cli link --user alice --ig-uid 100 --threads-uid 200 --base-dir ./data then python -m dual_index.cli read --user alice --base-dir ./data --output json showing a linked dual record, and python -m dual_index.cli rename --from bob --to alice --base-dir ./data only succeeding when alice is free in both universes, otherwise returning an error and leaving both stores unchanged.

Keep everything file-backed, deterministic, and offline. Hidden tests for this step will exercise link, unlink, and rename through both the Python API and the command-line tool, including simulated crashes and concurrent attempts on the same usernames (including rename with opposite order like rename alice→bob concurrent with rename bob→alice) to verify per-universe file-backed locking, ordered acquisition, and automatic recovery with error responses, not via direct file edits.
