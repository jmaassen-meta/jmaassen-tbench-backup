Now that the single and dual record formats and sharded storage are in place, let's add atomic cross-universe and cross-shard operations — the pattern that made the 1.5B/day username service hard. In production the username index is split by universe: IG and Threads each have their own sharded store, so even a single logical username touches two physical shard trees.

Please extend the model under /app/dual_index. The foundation from the previous step stays as-is (dual_index/encoding.py, dual_index/shard.py, dual_index/store.py, and the init/write/read commands). Hidden tests will import the exact new paths below via PYTHONPATH=/app.

| Module | Key symbols | Purpose |
|---|---|---|
| dual_index/atomic.py | AtomicIndex | Cross-universe, cross-shard atomic operations with per-row global locking |
| dual_index/cli.py (extended) | link, unlink, rename commands | Command-line entry points for atomic operations |

Add per-universe, cross-shard atomic operations in `dual_index/atomic.py` with an `AtomicIndex(base_dir, num_shards)` that maintains two separate sharded stores (`<base_dir>/ig` and `<base_dir>/threads`) under `base_dir`, a durable write-ahead log at `<base_dir>/wal.jsonl`, and per-username file-backed locks observable across processes as `<base_dir>/.lock_<username>`. Implement `link` and `read` with all-or-nothing semantics: `link` writes are journaled before being applied and committed after; a crash mid-`link` is expected to auto-recover to the pre-operation state, release locks, and **raise `ValueError`** (tests assert `ValueError`, not a generic exception — a `RuntimeError` would fail even though recovery happened); `read` is expected to never return a partial write and to silently reconcile a pending journal entry before returning committed state without raising, so the next mutating operation sees a clean state. `unlink` and `rename` are also expected to be atomic and respect the same lock/journal guarantees, but hidden tests for this step focus primarily on `link`/`read` atomicity and `rename` deadlock avoidance; if `unlink`/`rename` are implemented with the same WAL/lock pattern they will pass, but the core grading for this step is `link`/`read`. `rename` is expected to move a username across both universes and shards only when the destination is free in both, to reject same-name renames, and to acquire the two locks in sorted global order (`sorted([from_user, to_user])`) to avoid deadlock. Operations are expected to treat a pre-existing hold marker `<base_dir>/.hold_<username>` for any affected username as a held lock and fail with `ValueError` without creating a `.lock_` file or WAL entry and without leaving stale locks.

Observable file artifacts (tests assert these exact paths and shapes — match them):

- **WAL:** `<base_dir>/wal.jsonl` — append-only, one JSON object per line. For `link`/`unlink` each operation appends an `intent` entry before mutating shards and a `commit` entry after, sharing the same `id` (a UUID string). Intent schema for `link`: `{"id": "<uuid>", "op": "link", "username": "<name>", "old_ig": <prev IG record or null>, "old_threads": <prev Threads record or null>, "state": "intent"}` and the matching commit `{"id": same, "op": "link", "username": "<name>", "state": "commit"}`. For `rename`: `{"id": "<uuid>", "op": "rename", "from_user": "a", "to_user": "b", "old_from_ig": ..., "old_from_threads": ..., "old_to_ig": null, "old_to_threads": null, "state": "intent"}` plus matching commit. `old_*` are the exact shard records before the operation (or `null` if the username was absent). After success, `wal.jsonl` is expected to contain at least one `intent` and one `commit` with the same `id`, and there is expected to be no pending `intent` without a matching `commit` for completed operations (hidden tests assert this via `wal.jsonl` contents).

- **Locks:** `<base_dir>/.lock_<username>` — created exclusively (`open(..., 'x')`) at operation start after verifying no `.hold_` exists, held for the entire operation, and removed on success and on recovery. `test_link_no_lock_left_after_success` asserts no `.lock_alice` remains and that `wal.jsonl` contains both `intent` and `commit`.

- **Hold markers:** `<base_dir>/.hold_<username>` — externally created by tests via `Path(tmp, ".hold_alice").touch()` to simulate cross-process contention. If any affected username has a `.hold_` file, the operation must raise `ValueError` (without creating its `.lock_` and without appending to `wal.jsonl`) and leave no stale lock. Tests exercise this for `link`, `rename` (both `from_user` and `to_user`), and `unlink`.

- **Shard record shapes:** IG shards (`<base_dir>/ig/shard_{i}.json`) store the full dual record as produced by `encode_dual` / `encode_single` (keys `username`, `ig_uid`, `threads_uid`, `link_state`, `format` for dual). Threads shards (`<base_dir>/threads/shard_{i}.json`) store a record with the same values but the Threads uid under the key `uid` (not `threads_uid`), i.e. `{"username": "alice", "uid": 200, ...}` — `test_link_creates_both_universes` asserts `thr["uid"] == 200`. Preserve this shape.

Extend the CLI with `link`/`unlink`/`rename` subcommands and update `init` to create the per-universe trees (`<base_dir>/ig`, `<base_dir>/threads`) and an empty `wal.jsonl` if desired. Keep everything file-backed, deterministic, and offline. For grading, hidden tests verify via the Python API and CLI with file artifacts as observable side-effects — matching this file-backed contract is expected to guarantee a pass (tests check `wal.jsonl`, `.lock_`/`.hold_` presence and `thr["uid"]` shape as described).

Atomic API — `dual_index/atomic.py`

| Class / Method | Signature | Behavior |
|---|---|---|
| AtomicIndex | `AtomicIndex(base_dir, num_shards)` | Wraps two sharded stores (IG and Threads) under `base_dir` with crash-safe atomicity and per-username serialization. Any username being operated on is expected to be serialized across both universes until the operation is complete — either successfully committed or fully recovered — so the next operation sees a clean state. No explicit recover command is needed; recovery is automatic on next access. |
| link | `link(username, ig_uid, threads_uid)` | Atomically links a username: creates or updates the dual state by writing the username to both IG and Threads shards in one all-or-nothing operation. Is expected to serialize on that username across both universes for the entire operation. On crash, is expected to auto-recover both universes, release locks, and raise `ValueError`, leaving both stores in pre-operation state (tests check `pytest.raises(ValueError)` after a pending WAL entry). |
| unlink | `unlink(username)` | Atomically unlinks a username: removes the Threads entry and updates the IG entry to unlinked. Is expected to serialize across both universes with same auto-recovery. Raises `ValueError` if absent or already unlinked. |
| rename | `rename(from_user, to_user)` | Atomically moves a username across both universes and shards only if destination is free in both, preserving `ig_uid`, `threads_uid`, `link_state`, `format` and updating `username` to `to_user`. Is expected to serialize on both usernames in sorted global order to avoid deadlock and fail with `ValueError` if `from_user == to_user` or `from_user` absent or `to_user` taken. On crash, is expected to auto-recover both universes, release locks, and raise `ValueError` (same as `link` crash recovery). |
| read | `read(username)` | Returns the decoded record or `None`, reflecting only committed state across both universes. Is expected to respect ongoing serialization and silently auto-recover any pending journal entry before returning committed value without raising, so the next mutating operation sees a clean state. |

CLI — new commands on `python -m dual_index.cli` (all must be added to the same `cli.py` and work via `python -m dual_index.cli <command> --help`)

| Command | Options | Behavior |
|---|---|---|
| link | `--user NAME --ig-uid A --threads-uid B --base-dir PATH` (default `./data`) | Atomically links via `AtomicIndex` link. Serializes on that user across both stores; on crash auto-recovers and exits non-zero. |
| unlink | `--user NAME --base-dir PATH` | Atomically unlinks across both universes, same serialization and recovery, non-zero on failure. |
| rename | `--from USER --to USER --base-dir PATH` | Atomically renames across both universes and shards only if destination free. Serializes on both usernames in deterministic order; on crash auto-recovers and exits non-zero. |

Existing `init`, `write`, and `read` commands keep working as before, but `init` should now create the per-universe sharded trees and record shards and format. The new operations should be usable like `python -m dual_index.cli link --user alice --ig-uid 100 --threads-uid 200 --base-dir ./data` then `python -m dual_index.cli read --user alice --base-dir ./data --output json` showing a linked dual record, and `python -m dual_index.cli rename --from bob --to alice --base-dir ./data` only succeeding when alice is free in both universes.

Keep everything deterministic and offline. Hidden tests for this step will exercise `link`, `unlink`, and `rename` through both the Python API and the command-line tool, including simulated crashes and concurrent attempts on the same usernames (including opposite-order renames) to verify atomicity, crash recovery, and serialization without via direct file edits.
