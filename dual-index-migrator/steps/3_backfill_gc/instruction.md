This mirrors the 435M dangling cleanup and 20B backfill verification, where the username index pointed to a user blob whose stored username did not match.

User Store API — dual_index/user_store.py

| Class / Method | Signature | Behavior |
|---|---|---|
| UserStore | UserStore(base_dir, num_shards) | File-backed store for user blobs sharded by uid, stored under base_dir (e.g., base_dir/users). Each blob is a dict that must contain username (str, same lowercase 3-30 rules as the index — `^[a-z][a-z0-9._]{2,29}$`), uid (int) equal to the key it is stored under, and universe (str, must be `"ig"` or `"threads"`); extra keys are allowed and ignored. Universe is immutable — once a blob is created for a uid with universe `ig` or `threads`, a later `put` for that same uid with a different universe must raise `ValueError` and not modify the stored blob. All universe rules are tested via the API, not via simulated file corruption. |
| put | put(uid, blob) | Stores a blob for the uid, picking the shard deterministically via a stable hash (not Python's salted `hash()`), preserving the blob exactly. Raises `ValueError` if uid is not an int, blob is not a dict, or required keys are missing or universe is not `ig`/`threads`, or username fails validation, or uid does not match `blob["uid"]`, or universe would mutate an existing blob's universe. Is file-backed under base_dir so CLI and API see the same data. |
| get | get(uid) | Returns the blob dict for the uid or `None` if absent |
| shards | shards() | Returns `num_shards` |

Backfill API — dual_index/backfill.py

| Function | Signature | Behavior |
|---|---|---|
| backfill | backfill(base_dir, num_shards) | Scans all shards in both IG and Threads index trees and in the user blob store under base_dir. For every username it checks the current format and the corresponding blobs: single-format entries should be flagged as needing backfill to dual, dual entries should have consistent IG, Threads, and blob state. It should verify that the index's username matches the blob's username for each pointed-to uid, that the blob's universe matches the expected universe for that index entry (IG index entries must point to blobs with universe ig, Threads index entries must point to blobs with universe threads), and that the blob's universe has not been mutated. It must not create missing blobs — it only verifies and reports. Returns a dict with counts like total, already_dual, needs_backfill, consistent, inconsistent, and errors. Must be idempotent — running it twice should report the same counts. Each username check should respect per-username serialization — if a username is currently locked (including an external hold condition), it should be skipped or reported as busy, not deadlock. All checks are via the API. |
| gc_dangling | gc_dangling(base_dir, num_shards) | Scans the username index (both IG and Threads trees) and the user blob store for dangling pointers — cases where the index points to a uid whose blob is missing, or where the blob's stored username or universe does not match the index's username and expected universe, or where a Threads index entry exists without a corresponding IG entry. For a mismatched blob.username, repair should work as follows: if the blob's username is available in the index (meaning no index entry exists for that blob username, or the index entry for that blob username already points to this same uid), then update the available index entry to point at the blob and delete the initial mismatched index entry; otherwise, if the blob's username is not available (already taken by a different uid), then update the blob's username to match the original index lookup (keeping blob.universe unchanged, since universe is immutable). This repair must be per-username atomic and crash-safe and must not create missing blobs beyond the repair. Returns a dict with counts like scanned, dangling_found, repaired, removed. |
| verify | verify(base_dir, num_shards) | Scans all shards in the index and blob stores and checks that every index record decodes cleanly, that single-format entries have no Threads counterpart and have a matching blob with universe ig, that linked entries have both IG and Threads index entries and blobs for both uids with matching usernames and correct universes, and that unlinked entries have no Threads entry and only an ig blob. Also checks that no index points to a blob whose username or universe differs, and that no blob has had its universe mutated. Returns a dict with total, consistent, inconsistent and a list of inconsistent usernames. Does not modify data and does not create blobs. |

Atomic coordination with blobs — from this step onward, the atomic operations introduced in the previous step (link, unlink, rename) must also atomically coordinate the user blob store. For example, link should create or update blobs for the new ig_uid and threads_uid with the correct universe and username, unlink should handle the blob for the unlinked state, and rename from bob to alice must atomically move the index entries for both usernames across both IG and Threads shards *and* update the corresponding blob(s) for the moved uid(s) so that blob.username matches the new index username and blob.universe remains correct and immutable. Each of these operations must first verify that the target blob's universe matches the expected universe for the index entry being written and must fail without modifying if the universe would be mismatched or mutated. All of these must use the same per-username serialization as the index writes, so a crash leaves index and blobs either fully updated or untouched. All universe rules are tested via the API — hidden tests will verify that attempts to mutate universe or write with mismatched universe fail via the API.

Storage detail — keep it simple and deterministic. backfill, gc, and verify should iterate over the sharded stores under base_dir using the stable sharding already used for the index and for the blob store. They must respect per-username serialization — if a username is currently under an externally held condition, they should skip it or report it as busy, not deadlock or leave a partial. The exact counts and scan order are up to you, as long as verification is deterministic and gc that is interrupted does not leave orphans. You choose the on-disk representation consistent with these guarantees; hidden tests verify behavior via API/CLI, not file layouts.
